\subsection{From source text to executions}
The source3 method fixes C bytes, parses the supported C99 fragment into
a statement tree, and proves the equality between the parsed region
and that tree. Execution theorems then reason about this bound tree
under explicit state, memory and word-range contracts. This separates
the source identity from the value-level argument. It is a fragment
semantics, not a verified general C compiler.\src{C11}

For example, \code{KeygenMkgm3Program.source_bound} states
\[
 \code{C99ModularParser.region}\ 2945\ 91=\mathrm{some}\ \code{code}.
\]
The B1.02 execution work derives loop counters and pointer positions
for the first, triple and intermediate loop families of
\code{modp_NTT3_ext}. Butterfly-call observations are conclusions of
executions of the parsed bodies; assuming the intended calls would
leave the source-binding obligation unanswered. These are scoped
execution results, still subject to their memory and non-overflow
premises.\src{C11}

The generator certificate is similarly concrete. With
$p=2147355649$ and $g=1907584673$, the declarations in
\code{KeygenGeneratorOrder} prove
\begin{align*}
 g^{9216}\bmod p&=1,&g^{4608}\bmod p&\ne1,&g^{3072}\bmod p&\ne1,\\
 (g^2)^{4608}\bmod p&=1,&(g^2)^{2304}\bmod p&\ne1,&
 (g^2)^{1536}\bmod p&\ne1.
\end{align*}
The same module checks $9216=2^{10}3^2$ and $4608=2^9 3^2$.
These are the exact power tests used as the order certificates for
$9216$ and $4608$; they do not assume an NTT correctness oracle.
We quote the literal arithmetic declarations rather than silently
replacing them by a stronger source-level transform theorem.\src{C11}

\subsection{The verification found bugs}
\paragraph{F-001: an inherited C buffer-cursor defect.}
In the pinned \code{falcon_prng_get_bytes}, the available length is
computed from \code{p->ptr}, but the copy is
\code{memcpy(buf, p->buf.d, clen)} rather than a copy from
\code{p->buf.d + p->ptr}. A call beginning at a nonzero cursor can
therefore copy the buffer prefix instead of the intended stream slice.
The recorded census found the same statement in seven vendored
reference/optimized/local copies and no call sites in the examined
profiles. This is an inherited defect in the upstream lineage as
vendored here, classified LATENT; it is not evidence about every later
upstream release. The examined signing path uses the indexed
\code{get_u8}/\code{get_u64} accessors. A future use of the bulk-byte
API would activate the faulty path.\src{C12}

\paragraph{A dead REV10 parser branch.}
The initial store parser never recognized real expressions of the form
\code{gm[b + REV10[u << k]]}. Its greedy \code{pureExpr} consumed
\code{+ REV10} as part of a scalar expression, leaving a bracket behind.
The correction splits at the REV10 marker before parsing the base.
An apparently plausible row model would otherwise have described an
unbound program tree. This was a formal-model defect, not a new defect
in the C table.\src{C12}

\paragraph{Duplicated XOR and a false function call.}
The candidate \code{divSelect} included an outer XOR with \code{z},
although the compound update \code{z ^= ...} already supplied that
operation. Kernel checking rejected the claimed parse equality.
The correction uses precisely the right-hand side
\code{(z ^ z2) & -(uint32_t)((e >> i) & 1)}.
A separate parser pattern treated an opening parenthesis as a function
name and misread \code{((size_t)1 << k) - 1}; a token-name guard removed
the false call. The failed bindings and probes are retained in the
batch record.\src{C12}

\paragraph{What the traps teach.}
These cases motivate three checks. Parse equalities must concern the
actual source expressions. Calls and counters must follow from the
executed bodies, not from a list of intended operations. Finally,
theorem hypotheses must express the advertised experiment: a predicate
quantifying over all events remains statistical even if its name says
``PRF'' (Section~\ref{sec:computational}). The records retain the failed
bindings as well as the selected successful runs.\src{C11,C12,C15}

\subsection{Why the proved objects are the implementation's objects}
The propositions of Section~\ref{sec:b1status} might read as statements
about abstract vectors. They are statements about the same execution,
the same key material and the same bytes that the pinned code produces,
and it is worth being explicit about why.\src{C11,C21}

\paragraph{Same execution.}
The parse equality binds the exact source region --- bytes at pinned
paths --- to a statement tree, and the execution hypothesis of each
proposition is the run of \emph{that} bound tree under explicit state,
memory and word-range contracts. It is not an idealized algorithm that
happens to share a name with the source. Loop counters, pointer
positions and even the called butterflies are conclusions of executing
the parsed bodies (Section~\ref{sec:binding}, first subsection), so a
claim about the run is a claim about the code as written.\src{C11}

\paragraph{Same key.}
The conclusions quantify over the final heap of that very run and the
caller's own output-slot pointers: the four slots \emph{represent} the
four vectors of the NTRU equation, and the public-computation
proposition shows the same $f,g$ byte blocks are retained across the
call, so the resulting $h$ is computed from the retained material
rather than from fresh, unrelated inputs. The object of the equation
and the object in memory are the same vectors, by representation, not
by naming.\src{C21}

\paragraph{Same bytes.}
Block identity, extents and permissions are premises of the memory
contracts; the static tables are preserved through byte-block
properties; and the solver's modular check is consumed with a computed
residual rather than assumed. What this does \emph{not} give is the
global byte-level composition of serialization, verifier verdict and
caller-visible failure --- that is the open A3/A4 bridge
(Assumption~\ref{ass:a34}). A parse equality is also not a verified C
compiler, and each proposition speaks about a completed normal
execution of its fragment, not about every execution of the enclosing
loop.\src{C11,C21}

\subsection{The closed material propositions and the stage ledger}\label{sec:b1status}
The source-to-law work proceeds in named stages whose Acceptance blocks
define their exact scope; the stage names are bookkeeping recorded in
the compliance table of Appendix~\ref{app:compliance}. Here the two
closed results appear as ordinary propositions, in the order of the
argument: source execution, then the material and the equations it
satisfies. Neither proposition is a claim about the whole
\code{KeyGen} loop, its termination, or the distribution of emitted
keys, and both remain \NOTREVIEWED{} --- ``closed'' means
kernel-scoped at the stated fragment boundary. Neither closes arrows
1--2 of Section~\ref{sec:main}.\src{C21}

\begin{proposition}[Exact integer NTRU equation at the solver-chain
 boundary]\label{prop:ntru}
Under the entry contract of the caller fragment --- profile slots, the
pinned static table objects, legal scratch and disjoint output buffers,
and no coefficient, bound or equation facts --- suppose the parsed
solver region executes from caller entry through the complete root
call and returns normally. Then there exist integer vectors $f,g,F,G$
with coefficient bounds $1/1/2047/2047$ such that
\[
 f\cdot G-g\cdot F=q
\]
in the module's \code{multiply}/\code{constantCoeffs} coefficient
quotient, and each of the four output slots represents the
corresponding vector in the final memory. The solver's modular check is
consumed with residual $37748737<2147355649$; it is not a premise.
\end{proposition}
This is a source-fragment and object-reference composition theorem:
completed execution of the indicated fragments under legal initial
memory with an active root. It says nothing about the enclosing key
loop, an emitted key, or any security property.\src{C21}

\begin{proposition}[Public-key equations on the same material]%
\label{prop:pubkey}
Under its profile, legal-memory, material, bound-$1$, table-liveness
and output-separation premises, if the fixed public computation of the
fragment succeeds, then the same $f,g$ bytes are retained and there
exist $h$ and $\mathrm{fInv}\in\Rq$ such that the output slot holds the
canonical representation of $h$, the evaluations of $f$ are nonzero,
and both equations
\[
 h\cdot f=g
 \qquad\text{and}\qquad
 \mathrm{fInv}\cdot f=1
\]
hold in $\Rq$ in the module's \code{mulRq}/\code{reduceVec}
semantics. The witness $\mathrm{fInv}$ is mathematical; it is not a
serialized array. No correctness, invertibility or round-trip premise
is introduced: the equations are conclusions of the executed source.
\end{proposition}
This closes the local public/inverse/equation gap only; it is not a
whole-keygen statement and carries no independent review.
\src{C21}

In the stage ledger, the solver-chain stage behind
Proposition~\ref{prop:ntru} and the public-computation stage behind
Proposition~\ref{prop:pubkey} are closed at their stated scope; the
enclosing invocation stage is in progress. That stage is a partial
proof: its Acceptance block is not met and it is not reviewed.
Complete randomness-readiness and first-sampling boundaries have been
derived at the current checkpoint; the remaining obligations are the
full enclosing make invocation and control, the loop chronology
including the attempt cap, the six-gate accepted attempt, and the
transport of accepted material to the encoding inputs. Batch-level
records for all three stages are pinned in Appendix~\ref{app:compliance}.
\src{C21}

Deterministic execution traces license no IID model, no $p_{\mathrm{accept}}$
value and no availability formula; the measured acceptance rate of
Section~\ref{sec:parameters} remains an empirical control. The realized
attempt shape, the honest-signing hop and the law bindings of
Section~\ref{sec:main} remain open at every status of this ledger.
\src{C02,C08,C21}

\subsection{Proof engineering and current boundary}
The REV10 certificate now states
\code{rawTable = some ((List.range 1024).map bitrev10)}.
Its source-side certificate uses eleven slices, each parsing at most
eight pinned lines, and composes intermediate equalities without
re-parsing the entire table. Eight lines was the successful granularity
in the recorded experiment, not a universal limit of Lean's kernel.
The final named job is \code{keygen_rev10_cert_004}; the checkpoint
records a clean accepted run.\src{C11}

These results illustrate why a kernel proof of a model and a proof
that the model describes the source are distinct obligations. The
stage ledger of Section~\ref{sec:b1status} records how far the
source-to-law chain has been derived: the exact integer NTRU equation
(Proposition~\ref{prop:ntru}), the public $h$ and both equations on the
same material (Proposition~\ref{prop:pubkey}), and the enclosing
invocation stage still in progress. Their completion cannot be
inferred from the closed parser or table certificates, and the
remaining B1 obligations --- enclosing control, loop chronology, the
accepted attempt and the material-to-encoding transport, followed by
the emitted-material-to-law interfaces --- are still named gaps, not
consequences of the theorem names.\src{C11,C21}
