== Cel i metoda ==
Porównanie bajtowe prymitywów Rust (`ft-threshold-core`) z rzeczywistym
źródłem silnika FT1536 z `Extra/c`, nie z kopią ani z modelem Python.
Harness C (`impl/ci/engine_diff/probe_engine.c`) robi
`#include "falcon-vrfy.c"`, więc używa tych samych `static`
`mq_NTT_ternary`/`mq_iNTT_ternary`/`mq_mkgm3`/`mq_montymul`; do
`falcon_hash_to_point` linkuje `falcon-enc.c` i `shake.c`. Linkowanie z
`-ffunction-sections -fdata-sections -Wl,--gc-sections` odcina nieużywane
funkcje (fpr/keygen/sign/verify), nie zmieniając kodu testowanych ścieżek.

Program Rust (`crates/ft-threshold-core/examples/engine_diff_probe.rs`)
liczy te same przypadki przez publiczne API crate'a. Oba programy zapisują
identyczny format `FTDIF01` v1: nagłówek + 32-bajtowy SHAKE256 z
serializacji wyniku (`N` wartości `u16` little-endian). `run.py` porównuje
pliki bajt po bajcie.

== Co dokładnie porównano ==
- `hash_to_point`: nonce 16 B || msg 32 B, SHAKE256 (capacity 512,
  rate 136 B), rejection `w < 65536 − (65536 mod 18433)`, 1536 współczynników.
- NTT ternarna: dowolny wektor 1536 współczynników w `0..q−1`.
- iNTT ternarna: dowolny wektor w dziedzinie NTT.
- Mnożenie w `R_q` ścieżką silnika: NTT(a), NTT(b), `mq_poly_montymul_ntt`,
  `mq_poly_tomonty`, iNTT — odpowiednik `ntt::mul` w Rust (który ma
  osobny test vs szkolne `Poly::mul` i niezależny KAT Python).

== Napotkane pułapki harnessu (zachowane jawnie) ==
1. Pierwszy dym użył `shake_init(&sc, 256)` (SHAKE128) zamiast 512
   (standardowy SHAKE256, zgodny z `falcon_vrfy_start`). Dostałem inne
   wektory; to był błąd harnessu, nie rozjazd implementacji. Poprawka:
   512, potem zgodność.
2. W kategorii `mul` C początkowo przeplatał współczynniki `a` i `b`
   (`a[u]`, `b[u]` w jednej pętli), a Rust pobierał najpierw całe `a`,
   potem całe `b`. Ten sam generator, inna kolejność → różne wielomiany
   i fałszywy rozjazd 96 B. Poprawka: najpierw całe `a`, potem całe `b`.
   Kolejność jest teraz częścią kontraktu formatu w README.
Oba przypadki pokazują, że porównanie bajtowe faktycznie wykrywa różnice
wejść, a nie tylko „przepisuje” wynik.

== Czego ten dowód NIE obejmuje ==
- To nie jest niezależny odbiór (autor ≠ recenzent pozostaje wymagane).
- To nie jest dowód poprawności silnika ani bezpieczeństwa protokołu;
  pokazuje tylko zgodność czterech prymitywów na 4×10⁴ przypadkach.
- Nie porównano: FFT/`ffSampling`, sampler Kleina/Gaussa, keygen, sign,
  verify, norm check, wire/CBOR, ścieżki binarnej `q = 12289`, innych `logn`.
- Brak coverage-guided fuzzingu i analizy mutacyjnej (WP-022).
- `hash_to_point` jest jawny (nie MPC); SHAKE na udziałach (O-16) pozostaje
  otwarty.
- `PROD` nadal zablokowane przez `ProdEvidenceMissing` (O-05).
